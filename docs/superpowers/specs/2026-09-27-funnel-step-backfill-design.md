# Независимая доставка новых шагов прогрева уже идущим пользователям

Дата: 2026-09-27
Статус: утверждён

## 1. Задача

Заказчик расширяет воронку прогрева уже после запуска: например, было 2 шага, часть людей их уже
получила, теперь нужно добавить 3-й (и дальше). Сейчас новый шаг такие люди не увидят вообще — цепочка
достраивается один раз в момент выдачи материала и больше не пересматривается. Нужно, чтобы каждый
аккаунт продолжал получать прогрев с того места, где остановился, без дублей и без «взрыва» рассылки
по всей базе разом.

## 2. Как это работает сейчас (причина, не баг в обычном смысле)

`FunnelRepo.enqueue(user_id, now)` вызывается один раз — из `deliver_material` сразу после выдачи
материала. Она проходит по **всем шагам, которые существуют на этот момент**, и ставит каждому
`due_at = now + delay_seconds` (`now` ≈ момент выдачи материала). `INSERT OR IGNORE` защищает только от
повторной вставки одного и того же шага одному и тому же человеку — но новый шаг, добавленный позже,
никто повторно не вставляет для тех, кто уже прошёл `enqueue` раньше.

## 3. Решение (утверждено с заказчиком в диалоге)

Когда шаг **создаётся** или **включается обратно** (был выключен, стал включён) — сразу поставить его
в очередь всем, кто уже получил материал, по формуле:

```
due_at = users.material_sent_at (свой, персональный) + funnel_steps.delay_seconds (нового шага)
```

Не `сейчас + задержка` — а от личного момента входа в воронку каждого человека. Поэтому у тех, кто в
воронке уже несколько дней, время задержки нового шага чаще всего уже прошло — они получат его на
ближайшем тике планировщика (выглядит как «сразу»); у тех, кто зашёл недавно — по-настоящему в свой
черёд, отсчитывая от их даты.

**Вставка не в конец, а в середину цепочки.** Если новый шаг встаёт по позиции раньше, чем то, что
некоторые уже получили — таким людям он не ставится в очередь: только тем, кто ещё не получал ни одного
шага с более поздней позицией (`fs.position > <позиция нового шага>` и статус `'sent'`). Не пришедший
вовремя, но уже пропущенный (`'skipped'`, например из-за незавершённой подписки) в счёт «уже дальше» не
идёт — раз шаг не дошёл, человек не считается прошедшим дальше.

**Нагрузка.** Планировщик и так забирает не больше `BATCH=200` просроченных шагов за тик (раз в
минуту, `bot/scheduler.py`) — большая база «резко просроченных» шагов у давних пользователей разберётся
за несколько тиков сама, без дополнительного троттлинга.

## 4. Реализация

Один новый метод в `bot/repo/funnel.py`, чистый SQL (без цикла по пользователям в Python — то же, что
уже делает `segment_ids`/`_admin_exclusion` в `UsersRepo`, стиль соответствует остальному репозиторию):

```sql
INSERT OR IGNORE INTO user_steps(user_id, step_id, due_at, status)
SELECT u.tg_id, :step_id, u.material_sent_at + :delay_seconds, 'pending'
FROM users u
WHERE u.material_sent_at IS NOT NULL
  AND NOT EXISTS (
      SELECT 1 FROM user_steps us
      JOIN funnel_steps fs ON fs.id = us.step_id
      WHERE us.user_id = u.tg_id AND fs.position > :position AND us.status = 'sent'
  )
```

Вызывается из двух мест:
- `FunnelRepo.add_step(...)` — сразу после вставки нового шага, тем же вызовом (уже знает `step_id`,
  `position`, `delay_seconds`).
- `FunnelRepo.update_step(step_id, **fields)` — если среди полей есть `enabled` и до вызова шаг был
  выключен (`enabled=0`), а после — включён (`enabled=1`). Не срабатывает на изменении текста/медиа/
  кнопок/задержки/позиции и не срабатывает при выключении.

`UNIQUE(user_id, step_id)` (уже есть в схеме) не даёт продублировать шаг тому, кому он уже когда-либо
вставлялся — обычный `enqueue()` при следующем `/start`-заходе новых людей этот шаг тоже не задублирует.

Ничего не меняется в: `due_steps()`, `_process()` в `bot/scheduler.py`, самой отправке — вся логика
доставки уже умеет работать с очередью как есть.

## 5. Что нарочно не трогаем

- Изменение задержки/текста уже существующего шага не пересчитывает `due_at` тем, кому он уже стоит в
  очереди — так было и раньше, отдельная тема, не входит в этот запрос.
- Импорт цепочки (`FunnelRepo.import_json`) уже удаляет `user_steps` и пересобирает всё заново — это
  осознанное поведение «заменить воронку целиком», и оно не меняется: после импорта новая цепочка
  достанется всем активным как обычный первый `enqueue`, backfill здесь ни при чём.
- Обнуление статистики (`🧹 Обнулить статистику`) удаляет `user_steps`/`users` целиком — после этого
  backfill просто не находит, кому что доставлять, это ожидаемо.

## 6. Данные

Новых таблиц и колонок не требуется — используются существующие `users.material_sent_at`,
`funnel_steps.position`, `user_steps.status`.

## 7. Тестирование

- Добавление 3-го шага: пользователь с материалом «3 дня назад» получает его почти сразу (due_at в
  прошлом), пользователь с материалом «час назад» — через оставшееся время, отсчитанное от его даты.
- Вставка шага между уже существующими: пользователь, уже получивший более поздний по позиции шаг, не
  получает вставленный; пользователь, ещё не дошедший до него — получает.
- Пропущенный (`skipped`) более поздний шаг не считается «уже дальше».
- Повторное сохранение того же шага (правка текста/кнопок/задержки) не плодит вторую запись в очереди
  и не двигает уже стоящий `due_at`.
- Включение ранее выключенного шага запускает бэкфилл; выключение — нет.
- У кого материал ещё не выдан — не участвуют (нет `material_sent_at`), обычный текущий `enqueue()` при
  выдаче материала подхватит всё как есть.
