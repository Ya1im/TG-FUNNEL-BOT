# Ограниченный доступ заказчиков к админке + документ по пользованию

Дата: 2026-09-27
Статус: утверждён

## 1. Задача

Заказчики (эксперт и продюсеры) сейчас видят только текстовую статистику по `/stats`. Они попросили
доступ к самой админке, чтобы самостоятельно вести контент — без вашего участия — но без риска что-то
сломать или отобрать доступ друг у друга. Отдельно нужен документ, который вы отправите заказчику: что
он теперь может делать в своей части бота.

## 2. Решения (утверждено с заказчиком в диалоге)

| Вопрос | Решение |
|---|---|
| Модель доступа | Одна общая таблица приглашённых с полем «роль»: `stats` (как сейчас) или `admin` (новое). Владелец бота (`ADMIN_IDS` в `.env`) — отдельный, всегда полный доступ, не хранится в БД |
| Что видит роль `admin` | То же самое, что и владелец: Воронка (все 5 шагов, включая тексты подписки), Материал, Прогрев, Повторный /start, Рассылки (сбор/правка/отправка/планирование), Медиатека, «Тексты и кнопки», вся статистика |
| Что закрыто от `admin` | Управление доступами (кто админ/у кого `/stats`); смена канала проверки и закрытого канала; «Обнулить статистику»; удаление уже отправленной рассылки из истории; чат для пересылки отчётов (изменение настройки) |
| Свободное редактирование контента | Добавлять/убирать/менять местами блоки материала, шаги прогрева, блоки повторного /start, сообщения черновика рассылки — это обычное редактирование, не «опасное действие»; кнопки удаления там остаются |
| Приглашение | Тот же одноразовый инвайт-линк, что и для статистики (`t.me/бот?start=v_<токен>`), при создании ссылки владелец выбирает роль; либо добавление по ID |
| Документ по пользованию | Живой документ (как уже сделанная карточка бота), ссылкой — что можно делать в админке по разделам. Пишется после того, как код готов и проверен |

## 3. Данные

Расширяем то, что уже сделано для доступа к статистике (таблицы `viewers`, `viewer_invites`), а не строим
рядом вторую систему приглашений — это был бы дублирующий код и два похожих экрана в «Настройках»,
в которых легко запутаться самому.

- `viewers`: добавить колонку `role TEXT NOT NULL DEFAULT 'stats'` (`'stats'` | `'admin'`). Существующие
  записи получают `'stats'` — обратная совместимость, ничьи текущие доступы не меняются.
- `viewer_invites`: добавить колонку `role TEXT NOT NULL DEFAULT 'stats'` — роль фиксируется в момент
  создания ссылки и присваивается человеку при её использовании.
- Схема таблиц (`viewers`/`viewer_invites`) в БД не переименовывается — миграция того не стоит. В коде
  `ViewersRepo` → `AccessRepo` (`deps.viewers` → `deps.access`), потому что «viewer» (зритель) плохо
  описывает роль, которая умеет редактировать контент. Публичные тексты в боте и админке используют
  «доступ», не «просмотр».

## 4. Проверка прав

- `deps.config.is_admin(id)` — владелец (`.env`), как сейчас, без изменений.
- `deps.access.role(id)` → `None | "stats" | "admin"` — новый метод поверх таблицы `viewers`.
- Фильтр всей админки (`AdminFilter`, `bot/handlers/admin/common.py`) пускает владельца **или** того, у
  кого `role == "admin"` — так весь раздел `/admin` открывается заказчику с ролью `admin` целиком.
- Экраны, у которых часть кнопок — только для владельца, получают дополнительный параметр (id
  смотрящего) и рисуют владельческие кнопки только ему:
  - `settings_screen` — прячет «👥 Доступ к статистике» и «📤 Чат для отчётов»;
  - `subscription_screen` (раздел «Воронка» → «Проверка подписки») — прячет «📢 Канал для проверки» и
    «🔒 Закрытый канал», «✏️ Тексты и кнопки» остаются;
  - `stats_screen` — прячет «✏️ Чат для пересылки» и «🧹 Обнулить статистику», остальное остаётся;
  - `broadcast_card` — прячет «🗑 Удалить» у уже существующей рассылки.
- Спрятанная кнопка — не единственная защита: у каждого владельческого действия (`a:acc*`,
  `a:set:channel`, `a:set:private`, `a:set:force`, `a:set:report`, `a:stat:chat`, `a:stat:reset*`,
  `a:bc:del*`) обработчик сам проверяет `deps.config.is_admin(...)` и вежливо отказывает
  (`show_alert=True`), если кто-то нажмёт старую кнопку или подставит `callback_data` руками. Общий
  хелпер `require_owner()` в `bot/handlers/admin/common.py`, чтобы не повторять проверку текстом в
  каждом хендлере.
- `/stats` (`bot/handlers/viewer.py`) продолжает пускать и `stats`, и `admin` — заказчику с полным
  доступом не обязательно каждый раз открывать «Статистику» в админке.

## 5. Документ по пользованию

Отдельная живая карточка (как уже сделанная «Телеграм-бот — карточка для заказчика»), с разделами по
факту того, что реализовано: как получить доступ, что видно в «Воронке»/«Материале»/«Прогреве»/
«Рассылках», что нельзя и почему. Пишется после того, как функциональность реализована и проверена
тестами — раньше нечего было бы в неё честно записать.

## 6. Тестирование

- Миграция: старая база с ролью по умолчанию `stats` не теряет существующих зрителей.
- `AccessRepo`: приглашение с ролью `admin` через инвайт и через ID; роль сохраняется и читается.
- `AdminFilter` пускает роль `admin` в `/admin`, роль `stats` — не пускает.
- На каждом из четырёх экранов: с ролью `admin` владельческие кнопки не отрисованы; прямой вызов
  соответствующего `callback_data` отклоняется (`show_alert`), состояние не меняется.
- Обычные действия (материал/прогрев/повторный старт/рассылка: добавить, поправить, удалить черновик,
  переставить местами, отправить) у роли `admin` работают как у владельца.
- `/stats` отвечает и роли `stats`, и роли `admin`; постороннему — нет (без изменений).

## 7. Вне охвата

- Несколько уровней доступа сверх «только статистика» / «полный контент-доступ» — не запрашивалось.
- Аудит-лог «кто что поменял» — не запрашивался, можно добавить отдельной задачей, если понадобится.
