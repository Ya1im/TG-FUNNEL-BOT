# Память проекта: телеграм-бот воронки и рассылок

Контекст для будущих сессий. Коротко: что это, где живёт, чем чинится.

## Что это

Бот на холодный трафик: `/start` → кружок → меню с проверкой подписки на канал →
выдача материала → цепочка прогрева. Плюс массовые рассылки любым типом контента
по сегментам базы. Весь контент заливается через админку бота, в коде ничего не зашито.

За образец взят бот **@glazova_edu_bot**: кнопки «Канал» и «Проверить подписку»,
текст меню со ссылкой на канал (Telegram рисует превью), материал и прогревы —
картинка + текст + кнопка-ссылка.

Всё, что пользователь пришлёт не по сценарию (текст, медиа, стикеры, повторные команды) —
`bot/handlers/user.py:fallback` тихо удаляет сообщение, без ответа (в личных чатах бот может
удалять входящие сообщения без специальных прав). Повторный `/start` до получения материала
не шлёт кружок заново — только освежает текст меню (`services.send_menu`); кружок только на
самый первый заход (`services.send_welcome`). После получения материала `/start` шлёт блоки
«🔁 Повторный /start» (`⚙️ Настройки → 🔁 Повторный /start`, `bot/repo/repeat_start.py`) —
произвольная последовательность сообщений любого формата с кнопками, как у материала; пустой
список — осознанная тишина, не баг. Раньше здесь был один фиксированный текст
(`already_started_text`) — при первом запуске после обновления (25.09.2026) он один раз
автоматически переехал в первый блок (`services.migrate_repeat_start_blocks`).

Материал, прогрев и рассылка правятся прямо в боте: у уже созданного блока/шага есть
«✏️ Текст/медиа» (полностью заменяет содержимое, кнопки не трогает) и «🔘 Кнопки»
(меняет только кнопки-ссылки) — раньше можно было только добавить блок и удалить,
без правки задним числом. Рассылка (26.09.2026) перестала быть «слепой копией»
исходных сообщений админа: после «✅ Готово» открывается список собранных сообщений
(как список блоков материала) — по каждому можно посмотреть, поправить текст/медиа,
добавить кнопки-ссылки, поменять местами или удалить, и только потом выбрать сегмент.
Старые рассылки (до этой правки) по-прежнему шлются как раньше — движок понимает оба
формата `messages_json`.

## Стек и структура

Python 3.11, aiogram 3.15, aiosqlite (WAL), планировщик — своя asyncio-задача с тиком
раз в 60 секунд. Ни Redis, ни Postgres — сознательно.

```
bot/__main__.py      сборка бота, сессия (прокси при необходимости), планировщика
bot/config.py        .env → Config
bot/db.py+schema.sql база
bot/content.py       ContentBlock: текст + медиа + кнопки → вызовы Telegram
bot/sender.py        RateLimiter, safe_send (429 → ждём, 403 → blocked)
bot/subscription.py  ChannelGate.check()
bot/scheduler.py     тик прогрева, гейт подписки, переносы
bot/broadcast.py     движок рассылок с докатыванием после рестарта
bot/services.py      сценарии: старт, проверка, выдача материала
bot/repo/            users, media, funnel, material, repeat_start, broadcasts, settings
bot/handlers/        user.py + admin/{media,funnel,material,repeat_start,settings,stats,broadcast,capture,fallback}
bot/stats_export.py  пересборка .xlsx-таблицы статистики по расписанию (см. ниже)
```

Деплой — с мака одной командой:

```bash

```

Скрипт сам пушит локальные коммиты в GitHub, тянет их на сервер через `git pull` (не файлами —
именно git, `/opt/funnel-bot` теперь тоже репозиторий) и пересобирает контейнер с `--build`
(без этого флага поднимется старый образ — это уже наступали, см. грабли).

На первом запуске после перехода на git-деплой сервер попросит добавить deploy-ключ в
GitHub (Settings репозитория → Deploy keys, ключ скрипт сгенерирует и покажет сам) —
разовая настройка, дальше не потребуется.

`.env` и `data/` не в git и через `git pull` не обновляются — это осознанно (секреты и база
не должны попадать в репозиторий). Если меняешь `.env` локально, деплой это заметит по
хешу и подскажет скопировать вручную (`scp .env $SERVER:/opt/funnel-bot/.env`).

## Перенос на другой сервер (`migrate_server.sh`)

Двухшаговый безопасный перенос бота на новый сервер (например, чтобы уйти с российского
хостинга и убрать зеркало Telegram API, см. грабли №2):

```bash
cd ~/Desktop/тима
./migrate_server.sh prep    root@OLD_IP root@NEW_IP   # подготовка, простоя нет
./migrate_server.sh cutover root@OLD_IP root@NEW_IP   # переключение, простой — секунды
```

`prep` — ставит Docker на новом сервере, заводит для него отдельный deploy-ключ GitHub
(старый ключ с первого сервера не подходит — попросит добавить новый, один раз), клонирует
код, забирает боевой `.env` со старого сервера как есть, проверяет прямой доступ к
`api.telegram.org` с нового сервера (`getMe`) и если он есть — сам убирает
`TELEGRAM_API_BASE` из `.env` на новом сервере (зеркало больше не нужно); если прямого
доступа нет — оставляет зеркало как было, ничего не ломая. Собирает образ, но **не
запускает** контейнер — старый сервер всё это время работает без простоя. Можно гонять
`prep` сколько угодно раз, идемпотентно.

`cutover` — вот тут простой: гасит контейнер на старом сервере, переносит `data/` (SQLite
база) через локальную машину, поднимает контейнер на новом. Старый сервер после этого
только останавливается, не удаляется — план отката: `docker compose start` на нём же (но
учти, что сообщения, обработанные новым сервером после переключения, при откате на старую
базу потеряются).

## Грабли, на которые уже наступили


1. **`unable to open database file`** — папка `data` на хосте принадлежит root, а процесс
   в контейнере работает под uid 1000. Лечится `mkdir -p data && chown -R 1000:1000 data`.
2. **Бот виснет после «База подключена»** — хостер режет `api.telegram.org`. Раньше обходили
   зеркалом (`TELEGRAM_API_BASE`, личный Cloudflare Worker), но это создавало собственные
   проблемы (см. грабли №11, №12) — саму фичу зеркала убрали из кода 29.09.2026 после переезда
   на сервер, где Telegram доступен напрямую (см. ниже «Перенос на другой сервер»). Если хостинг
   снова начнёт резать Telegram — решение теперь: переезжать, а не городить прокси в коде.
   `TELEGRAM_PROXY=socks5://…` (`bot/config.py`, `Config.proxy`) как аварийный вариант остался.
3. **`docker compose up -d` без `--build`** после заливки кода поднимает старый образ.
   Симптом: новые логи/настройки не появляются, хотя переменная в контейнере есть.
4. **`file_id` привязан к боту.** Сменил токен — медиатеку заливать заново. Структура
   воронки переносится экспортом/импортом JSON (медиа ищется по slug).
5. **Роутеры aiogram — модульные синглтоны.** Второй `build_dispatcher` в том же процессе
   падает с «Router is already attached». В тестах спасает `tests/conftest.fresh_dispatcher`,
   который перезагружает модули роутеров.
6. **Git в подключённой папке** на маке не мог удалять свои lock-файлы, пока не выдано
   разрешение на удаление в этой папке. Симптом: `cannot lock ref 'HEAD'`.
7. **В настройках канала** принимаем только `channel/supergroup/group`: однажды сохранился
   сам бот, потому что на вход прилетела ссылка на него.
8. **Бот не может первым написать пользователю**, если тот ни разу не жал `/start` — платформенное
   ограничение Telegram, не баг. Актуально для «чата для отчётов» в 📊 Статистике: если эксперт —
   не группа/канал, а личный человек, ему сначала нужно самому запустить бота.
9. **Кружок (video_note) в рассылке падал с `VOICE_MESSAGES_FORBIDDEN`**, хотя это не
   голосовое — у Telegram это ОДНА настройка приватности «Голосовые и видеосообщения»
   на оба формата, и API возвращает один и тот же код ошибки для обоих. Раньше рассылка
   слала кружок как чистую копию (`copy_message`) и на этой ошибке засчитывала жёсткий
   `failed`. Починено (26.09.2026): `bot/sender.py:send_block` при этой конкретной ошибке
   на кружке пробует запасной вариант — тот же файл, но обычным видео (`bot/content.py:
   ContentBlock.fallback_factory`); работает и в материале/прогреве/повторном /start,
   и в рассылке (она теперь тоже строит `ContentBlock`, см. выше). Голосовые (`voice`)
   запасного варианта не имеют — это осознанно, менять формат голосового на файл сильно
   меняет опыт получателя.
10. **`preview()` резала HTML "как есть"** (`bot/handlers/admin/common.py`) — на длинном или
   отформатированном тексте обрезка по числу символов иногда попадала внутрь тега/сущности
   (`&amp;`), Telegram отвечал `can't parse entities`, и кнопка («✏️ Тексты и кнопки», список
   материала) вечно крутилась в загрузке, потому что `show()` падал раньше `call.answer()`.
   Починено (25.09.2026): `preview()`/`safe_excerpt()` сначала снимают разметку и только потом
   безопасно экранируют уже обрезанный текст; `show()` вдобавок подстрахован — если отрисовать
   экран не вышло вообще никак, шлёт понятное сообщение вместо тишины. См. тест
   `test_preview_never_breaks_html_on_long_rich_text`. **Если добавляешь новый экран с
   превью/куском пользовательского текста — используй `preview()`/`safe_excerpt()` из common.py,
   не режь HTML-строки руками.**

11. **Контейнер падал целиком при кратковременной недоступности зеркала Telegram API**
   (28.09.2026) — `bot.__main__.set_commands()` вызывал `bot.set_my_commands(...,
   scope=BotCommandScopeDefault())` без `try/except`; один таймаут при заходе через
   `TELEGRAM_API_BASE`-зеркало (см. грабли №2) на самом старте ронял весь `main()`
   необработанным `TelegramNetworkError`, ещё до начала polling. `restart: unless-stopped`
   сам поднимал контейнер заново, но это лишняя точка отказа. Починено: вызов обёрнут в
   `try/except` с `log.warning(...)`, как уже было сделано для команд по чатам админов
   строкой ниже. См. `tests/test_main.py::test_set_commands_does_not_crash_on_network_error`.

12. **Приветствие админу приходило с заметной задержкой** (28.09.2026) — `cmd_start`
   (`bot/handlers/user.py`) на каждый `/start` от владельца сначала **дожидался**
   `_sync_admin_commands()` (ещё один сетевой запрос к Telegram, `SetMyCommands`) и только
   потом слал welcome — то есть на каждый заход админа уходило два последовательных
   похода в Telegram API вместо одного, и на нестабильном канале до Telegram (зеркало,
   грабли №2) это удваивало и без того заметную задержку именно для владельца (обычные
   подписчики этот путь не задевают — `_sync_admin_commands` для них выходит рано). Починено:
   порядок вызовов поменян местами — welcome уходит первым, синхронизация меню команд
   (не влияет на то, что видит человек) — после. См.
   `tests/test_e2e.py::test_admin_start_sends_welcome_before_syncing_command_menu`.

13. **Обход через Cloudflare (зеркало Telegram API) убран из кода** (29.09.2026) — после
   переезда на финский сервер с прямым доступом к Telegram сама фича зеркала
   (`TELEGRAM_API_BASE`, `Config.api_base`, `TelegramAPIServer` в `bot/__main__.py`) больше не
   нужна и убрана целиком — не просто выключена в `.env`. Если когда-нибудь снова понадобится
   обходить блокировку — доступен только `TELEGRAM_PROXY` (SOCKS5/HTTP), зеркало придётся
   писать заново (это осознанно: держать в коде мёртвый, непроверяемый путь ради гипотетического
   будущего хостинга — риск больше пользы, см. грабли №11, №12, которые как раз в этом пути
   и жили).

## Структура админки (26.09.2026)

Главное меню — 4 раздела: 🧭 Воронка (`flow.py`), 📤 Рассылки, 📊 Статистика, ⚙️ Настройки. «Воронка» —
путь подписчика по порядку: 1 Приветствие (`a:flow:hi`), 2 Проверка подписки (`a:flow:sub`: канал,
закрытый канал, тексты подписки), 3 Материал, 4 Прогрев, 5 Повторный /start; у каждого пункта статус
✅/⚠️/➖ (`flow.flow_status`), на главном экране — «Осталось настроить…». В «Настройках» только общее:
медиатека, все тексты (по группам `TEXT_GROUPS`), чат для отчётов (`a:set:report`). Правило навигации:
кнопка «Назад»/«Отмена» ведёт в **свой** раздел (шаги воронки → `a:flow`, медиатека → `a:set`, ввод
канала → `a:flow:sub`); при правке текста возврат хранится в FSM-поле `back`. Списки блоков/шагов/
сообщений рассылки — по одной строке с иконкой типа (`common.item_label`), экраны собираются через
`common.screen_text` (заголовок + подсказка курсивом + список). Карточка шага прогрева двухуровневая
(«⋯ Ещё»: подписка, напоминание, вкл/выкл, порядок, удаление). Новый экран → тот же шаблон и тест в
`tests/test_e2e.py` (блок «структура админки»).

## Независимый бэкфилл шагов воронки (27.09.2026)

Новый или заново включённый шаг прогрева сам встаёт в очередь уже идущим пользователям — не только
новым. `FunnelRepo.backfill_step(step_id, position, delay_seconds)` (`bot/repo/funnel.py`) вызывается
из `add_step(..., backfill=True)` (по умолчанию, сразу при создании одного шага через админку) и из
`update_step` при переходе `enabled` 0→1. `due_at` считается от личной даты пользователя
(`users.material_sent_at`), не от `now()` — у тех, кто получил материал давно, шаг уйдёт на ближайшем
тике планировщика. Пользователю, уже получившему (`status='sent'`) шаг с более поздней позицией, новый
или повторно включённый шаг не ставится (`'skipped'` за «уже дальше» не считается) — так задним числом
никого не дублирует и не путает порядок. `bot/scheduler.py`, `due_steps` и отправка не менялись — тик и
так справляется с любым бэклогом.

- **Массовая загрузка не бэкфиллит.** `import_json` (пересборка всей цепочки) и `bot/seed.py`
  (первое наполнение пустой воронки) вызывают `add_step(..., backfill=False)` — это не «добавили один
  новый шаг», а загрузка с нуля; иначе после реимпорта вся цепочка задним числом ушла бы всем текущим
  пользователям разом (история отправок стёрта, сверяться не с чем).
- **Известное ограничение.** «Уже дальше» проверяется по позиции шага **на момент создания**
  (`add_step` всегда ставит шаг последним). Если админ вставляет шаг «в середину» через кнопки
  ↑/↓ (`move_step`) уже после создания, бэкфилл повторно не пересчитывается (перестановка позиций сама
  по себе бэкфилл не запускает) — редкий сценарий истинной вставки в середину цепочки этим не покрыт.
  На практике работает для главного случая — добавления шага в конец действующей цепочки — и для
  повторного включения уже существующего в середине шага.

Спека: `docs/superpowers/specs/2026-09-27-funnel-step-backfill-design.md`.

## Доступ клиентов к админке: роли `stats`/`admin` (27.09.2026)

Клиенты получают доступ по одной из двух ролей, обе хранятся в тех же таблицах `viewers`/
`viewer_invites` (колонка `role`, только код переименован — `AccessRepo`, бывший `ViewersRepo`):
- **`stats`** — только команда `/stats`, текстовый отчёт (`bot/stats_report.py`: люди, воронка с
  конверсиями, приток 24ч/7д/30д, источники, шаги прогрева, последние рассылки; админ-тестеры в цифры
  не входят) + кнопка «🔄 Обновить»; админка (`AdminFilter`) недоступна.
- **`admin`** — вся админка (`AdminFilter` пускает `deps.config.is_admin(...)` **или**
  `await deps.access.role(user_id) == "admin"`), кроме владельческих/опасных действий (см. ниже).

Владелец бота (`ADMIN_IDS` из `.env`) в БД не хранится и проходит любые проверки всегда, роль `admin`
никогда не даёт того же, что владелец. Доступ выдаётся в ⚙️ Настройки → 👥 Доступ к статистике
(`admin/access.py`, сам этот раздел и все `a:acc*` — владельческий): одноразовая ссылка
`t.me/<бот>?start=v_<токен>` (7 дней; `AccessRepo.redeem`) или добавление по ID/пересланному сообщению —
в обоих случаях сначала выбор роли. Клиент по ссылке/ID **не попадает в `users`**, воронку и статистику.
Чужой `/stats` не отвечает — сообщение тихо удаляет общий fallback. Роутер `viewer.py` стоит до `user.py`.

**Владельческие исключения** (роль `admin` их не видит на экране и получает отказ `require_owner()`
= `call.answer("Доступно только владельцу бота", show_alert=True)` при прямом обращении к
`callback_data`, без кэша — доступ проверяется заново на каждое нажатие):
весь раздел «Доступ к админке» (`a:acc*`, целиком владельческий роутер), смена канала проверки подписки
и закрытого канала (`a:set:channel`/`a:set:private`/`a:set:force`), чат для пересылки отчётов
(`a:set:report`/`a:stat:chat`), обнуление статистики (`a:stat:reset`/`a:stat:reset:go`), удаление
рассылки из истории (`a:bc:del`/`a:bc:delok`). Всё остальное (материал, прогрев, повторный /start,
черновик и отправка рассылки, вся статистика кроме обнуления, медиатека, любые тексты кроме смены
канала) роли `admin` доступно наравне с владельцем. Экраны-строители (`settings_screen`,
`subscription_screen`, `stats_screen`, `broadcast_card`) берут параметр `is_owner: bool`
(`deps.config.is_admin(<id вызвавшего>)`) и рисуют владельческие кнопки только при `is_owner=True` —
дырка «кнопка скрыта, но callback всё равно исполняется» не годится: обработчик и экран проверяют
владельца независимо друг от друга.

## Кнопка «Инструкция» в админке (28.09.2026)

5-й пункт главного меню админки (`a:guide`, `bot/handlers/admin/__init__.py`) — отправляет PDF
`bot/assets/client-guide.pdf` (`FSInputFile` + `answer_document`), видна и владельцу, и роли `admin`
(не владельческая, `require_owner` не нужен — просто пункт `MENU`). Если файла нет на диске — алерт
«Файл инструкции не найден, сообщите разработчику», не падение.

PDF — не источник истины, а сборка. Источник — `docs/client-guide/client-guide.md` (markdown,
не участвует в рантайме, не копируется в Docker-образ), генератор — `docs/client-guide/generate_pdf.py`
(reportlab, шрифты DejaVuSans/DejaVuSans-Bold для кириллицы, эмодзи из markdown вырезаются перед
рендером — `_strip_emoji()`, DejaVuSans их не умеет). **Обязательный процесс на будущее**: при каждом
функциональном изменении бота — правка `client-guide.md` (новая строка в «Историю изменений», + правка
раздела, если поменялся пользовательский сценарий) → перегенерировать PDF (`python
docs/client-guide/generate_pdf.py`) → закоммитить оба файла вместе с кодом изменения, не отдельным
коммитом «позже». Спека: `docs/superpowers/specs/2026-09-28-client-guide-pdf-design.md`.

## Проверка подписки (26.09.2026)

`ChannelGate.status()` возвращает `yes/no/error` — сбой Telegram (нет прав, канал не найден) больше
не считается «не подписан» и напоминаний не вызывает. Кнопка «Проверить подписку» по-прежнему
использует `check()` (bool). Напоминает бот **только там, где админ сам включил**:
- шаг прогрева с 🔒: «🔔 Если не подписан» — `skip` (по умолчанию, шаг молча пропускается) или
  `remind` (`funnel_steps.on_unsub`; интервал и число раз — настройки `gate_retry_hours`, `gate_max_attempts`);
- рассылка: «🔔 Проверка подписки» — `off` / `skip` / `remind` (`broadcasts.sub_mode`, текст —
  `resub_reminder_text`); в статистике появились «пропущено» и «напоминание получили».
Миграция в `db.py:_migrate` дописывает колонки в старые базы; уже настроенные шаги с 🔒 стали `remind`,
чтобы прод не поменял поведение молча. Общая функция отправки — `bot/reminder.py`.
